# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`mb-powermon.py` is a single-file curses TUI that monitors edge AI NPUs and external power-measurement devices on a workstation. It is adapted from `../envic_ai_python/ai_nvtop.py` with the AMD host probe removed; six probe types are supported: **hailo**, **axelera**, **deepx**, **memryx**, **elmorlabs** (PMD2), and **adafruit** (INA228 over FT232H).

`csv-to-html-plot.py` is an independent companion script that renders an mb-powermon CSV (the `--csv` side-output) as a self-contained HTML file with Chart.js power+temperature plots. It uses min-max bucket downsampling to keep long captures viewable, and with `-l <hailortcli.log>` overlays parsed avg/max markers on the matching device's active phase. The two scripts share no code — the only contract is the CSV column-name convention `<device>_POW / _TEMP / _TS0 / _TS1`.

There is no build, lint, or test suite — the tools are run directly.

## Common commands

```bash
# Live TUI (q/ESC quit, r reset, h help)
python3 mb-powermon.py

# One-shot text snapshot (good for piping/CI)
python3 mb-powermon.py --once

# TUI + line-buffered CSV side-output
python3 mb-powermon.py --csv run.csv

# Restrict probes (also controls top-to-bottom panel order)
python3 mb-powermon.py --probe adafruit,hailo

# Probe-init diagnostics to stderr (which SDK loaded, why temps are missing, etc.)
python3 mb-powermon.py --verbose

# Quick syntax check after edits (no test suite exists)
python3 -c "import ast; ast.parse(open('mb-powermon.py').read())"
```

`--device <ID>` filters to specific BDFs / serial port paths. `--ina228-shunt`, `--ina228-max-current`, `--ina228-addresses` tune the INA228 calibration. `--temp-max` / `--power-max` set the y-axis caps.

## Architecture

The whole program is one file. The interesting design is the **probe → Metric → TUI** decoupling — keep this contract intact when editing.

### The `Metric` contract

Every probe owns a `metrics` list of `Metric(label, history, unit, color_id, max_val)` namedtuples. `history` is a `deque` of `float | None` samples (newest at the right; `None` means "no reading"). The TUI never knows about specific probe internals — it iterates `probe.metrics` to draw inline bars, graph traces, the legend, and the CSV columns. **To add a new measurement, append a `Metric` to the probe's list and push samples in `poll()` — no TUI changes needed.**

`max_val=None` falls back to the TUI-level default (`TEMP_MAX` for °C, `POWER_MAX` for W — both driven by the `--temp-max` / `--power-max` CLI flags). Set `max_val` explicitly **only** when one metric needs a legitimately different scale from its peers (e.g. PMD2's `TOTAL` on a 100 W axis while `PCIE1/2/3` follow `--power-max`).

**Contract: probe-class `POWER_MAX` is intentionally NOT honored** by the TUI's `_metric_max()`. Earlier versions consulted `getattr(probe, "POWER_MAX", self.POWER_MAX)` so a probe class could "default" its own cap — but this had the surprising side-effect that probe-class defaults shadowed the user's `--power-max` CLI flag. Reverted 2026-05-21: `--power-max` is now authoritative for any "W" metric whose `max_val` is None. If a probe genuinely needs a different scale, use per-metric `max_val` (see PMD2's TOTAL). Don't add `POWER_MAX = N` class attributes — they're dead code and the lookup path that used them is gone. Same applies to setting `max_val=self.POWER_MAX` in metric construction: this would put a probe's notion of "default cap" at the top of the priority chain (above the CLI flag) — don't do it. INA228Probe historically did both; both have been removed.

The CP_* color-pair IDs are defined at module scope so probes can reference them during `__init__` — that runs **before** `curses.start_color()`, so don't move them into `_init_colors()`.

### The `state_flags` contract

Sister contract to `metrics`, for latching / multi-state status indicators (thermal-throttle, power-alert, OCP zone, etc.). A probe declares `self.state_flags = [<entry>, ...]` where each `<entry>` is a 2-, 3-, or 4-tuple — see immediately below. Deques hold the most recent integer per poll (`None` = no reading).

Each entry may be either:
- `(label, deque)` — the **2-tuple short form**. Values rendered via the binary default formatter (`_default_state_badge`): `0` → green ` OK `, non-zero → red `ALERT`, `None` → dim ` -- `. Standard bracketed-and-bold rendering: `LABEL [ OK ]`.
- `(label, deque, formatter)` — the **3-tuple custom form**. `formatter(value) -> (text, color_pair_id, attrs)`. Use when a flag has more than two states (e.g. Hailo `THERMAL`'s 5-state ladder −1 / 0 / 1 / 2 / 3 → OK / L1 / L2 / L3 / MAX). The renderer layers `A_BOLD` on top of the returned attrs. A misbehaving formatter (exception, wrong-shape return) falls back to the default — never crashes the panel.
- `(label, deque, formatter, plain)` — the **4-tuple plain form**. When `plain=True` the renderer skips the surrounding `[ ]` brackets **and** skips the implicit `A_BOLD` overlay — the value renders as low-key inline text rather than a loud badge. Pair with `_on_off_white_badge` (white `ON `/`OFF` / `-- `) for feature-enable flags that nearly always read the safe state at idle and don't deserve to visually compete with the more interesting indicators next to them. Used today for Hailo's `TEMP_PROT` and `OCP_PROT` — the panel reads `... THERMAL [ OK ]  TEMP_PROT ON   OCP [ OK ]  OCP_PROT ON` with the bracketed badges drawing the eye and the protection flags receding into the row.

**TUI rendering** — one left-aligned row sitting **between the stats row and the inline-bars row** (so the module-level latches read as part of the panel header, not buried between the bars and the graph), in the form `<PREFIX_LABEL> <prefix_value>  <FLAG_LABEL> [<state> [<state> ...]]  <FLAG_LABEL> <state>  ...` (some widgets bracketed, some plain):
- Each LABEL (`CLOCK`, `THERMAL`, `POWER`, `TEMP_PROT`, ...) is bold-cyan (`CP_ACCENT`), matching the `PRODUCT / DESCRIPTION` style on the stats row above.
- The optional prefix value (e.g. `850MHz`) is dim (`CP_DIM`).
- **Bracketed style** (2- and 3-tuple entries) — brackets `[` `]` are dim and the value inside is rendered by the per-flag formatter (or the default), with `A_BOLD` layered on. ` OK ` and ` -- ` keep the inner spaces intentionally so `[ OK ]` doesn't look cramped next to `[ALERT]`.
- **Plain style** (4-tuple entries with `plain=True`) — no brackets, no bold, value rendered as low-key inline text from the formatter (typically `_on_off_white_badge` returning white `ON `/`OFF` / `-- `). De-emphasizes flags that nearly always read the safe state at idle.
- **Group-by-prefix**: consecutive `state_flags` entries whose labels match `PREFIX_<digit>` (e.g. `THERMAL_0`, `THERMAL_1`, ...) collapse into one widget `PREFIX [ s0  s1  ... ]`, each inner badge colored from its own deque (and its own formatter — formatters are per-entry, so the entries in a group MAY have different formatters, though in practice they share one). Group's `plain` flag is the OR of its entries'. Non-grouped labels render alone. CSV always emits one column per per-chip flag — the grouping is purely a TUI cosmetic.
- Labels should be short, ALL-CAPS keywords — `THERMAL`, `POWER`, `LINK`, `OCP`. Avoid `_ALERT` suffixes; the colour and `[ALERT]` badge already convey state. Use `_PROT` suffix for feature-enable bits paired with the plain-form ON/OFF rendering (`_on_off_white_badge` + `plain=True`) — e.g. `OCP_PROT`, `TEMP_PROT`. The semantic is "is the protection feature switched on?" — `ON` is the safe state; `OFF` reads as the only non-`ON` token in the row, which is the actually-dangerous case worth surfacing without needing red coloring.

**Optional `state_prefix`** — `None` (default), a tuple `(label, value_str)`, or a zero-arg callable returning either. A bare string is also accepted and renders as `STATUS <value>` (fallback for ad-hoc probes that just want one number up front). All four NPU probes use it for **CLOCK**:
- **Hailo** — `("CLOCK", "<MHz>MHz")` driven by `current_temperature_throttling_level` (drops with the throttle tier: 400 → 350 → 300 → 250 → 200 MHz on this firmware).
- **MemryX** — `("CLOCK", "<MHz>MHz")` from `mxa.get_frequency()` (reflects 14T / 20T boost mode the SDK auto-clocked to).
- **Axelera** — `("CLOCK", "<MHz>MHz")` from `axr.Context().read_device_configuration()["clock_profile"]`, cached once at `_open()` (boot-time config; not adaptive on Metis M.2).
- **DeepX** — `("CLOCK", "<MHz>MHz")` parsed from `dxrt-cli -s` per poll (documented as static, re-parsed defensively in case a future firmware varies it).

The convention pays off when the prefix is paired with state-flag context — `THERMAL [ OK  OK ALERT  OK ]` on MemryX is much more interesting next to a known 850 MHz boost than at 600 MHz baseline. On Axelera/DeepX (no badges yet) the CLOCK alone is still useful: confirms which clock the chip booted at and stays put unless someone reconfigures it. The prefix is display-only — never logged to CSV (matches the user's "CLK is not a metric" decision).

**Layout cost** — `_draw_device()` reserves one extra row between the stats row and the inline-bars row when the probe declares **either** non-empty `state_flags` **or** a non-None `state_prefix` (pushing the bars + graph down by one), then `_draw_state_flags()` does the rendering. So Axelera/DeepX (prefix-only, no flags) and Hailo/MemryX (prefix + flags) all get one status row; PMD2 and INA228 (neither) skip the row entirely. Both `_csv_emit()` (TUI path) and `write_csv_snapshot()` (`--once --csv` path) iterate `state_flags` to emit one `<bdf>_<label>` column per flag — `state_prefix` is display-only, never logged to CSV. `do_snapshot()` prints both: first the prefix as `<LABEL> = <value>` (e.g. `CLOCK     = 400MHz`) and then one `<FLAG> = <int> (<text>)` line per state-flag entry, in declaration order — so the text snapshot mirrors the TUI status row left-to-right.

Probes with no enum status leave `self.state_flags = []` (or omit the attribute entirely — the TUI uses `getattr(probe, "state_flags", None) or []`). Two probes populate `state_flags`: `MemryXProbe` exposes per-chip `THERMAL_<i>` flags from `/sys/memx<N>/temperature` (sysfs, no SDK dependency) plus an optional module-level `POWER` from `mxa.get_poweralert()` (SDK-gated); `HailoProbe` exposes four flags from `device.control._get_health_information()`: `THERMAL` (5-state ladder via custom formatter), `TEMP_PROT` (feature-enable bit, ON/OFF), `OCP` (binary GREEN/RED zone), and `OCP_PROT` (feature-enable bit, ON/OFF).

**All four NPU probes (Hailo / MemryX / Axelera / DeepX) supply a `state_prefix`** rendering the current NN clock as `CLOCK <MHz>` ahead of any badges — the status row layout is uniform across backends even though the badge count varies (Hailo: 4 badges, MemryX: N+1 badges, Axelera/DeepX: 0 badges). The status row is reserved whenever a probe declares either `state_flags` or `state_prefix`, so the empty-badges case (Axelera/DeepX showing `CLOCK <MHz>` alone) still gets a row above the inline bars. PMD2 and INA228 supply neither and skip the row entirely.

### Probe interface

Every probe class implements:

- `__init__(self, ..., history_max=None)` — discover, open, populate `self.metrics`
- `bdf` (str) — display ID; PCI BDF for hailo/axelera, serial path for PMD2, `"adafruit-ft232h"` for INA228
- `pcie` (dict) — `pcie_info(bdf)` result, or `{}` for non-PCI probes
- `identity` (dict) — board_name / arch / product_name / description / part_number / serial
- `device` — truthy iff the SDK handle opened; `None` triggers the red `ERROR` row
- `error` (str | None) — short reason shown next to `ERROR`
- `poll()` — append exactly one sample (or `None`) to every metric's history
- `reset_history()` — clear all deques (bound to the `r` key)
- `close()` — release SDK / serial / collector state cleanly
- Optional `metrics_settled` (bool) — defers CSV header until labels finalize (INA228 uses this to wait for the rail-voltage classification that turns `P1` into `P1(3.3V)`)
- Optional `state_flags` (list) — non-numeric enum indicators (`[(label, deque) | (label, deque, formatter) | (label, deque, formatter, plain), ...]`); see "The `state_flags` contract" above
- Optional `state_prefix` (`None` / `(label, value_str)` tuple / callable / bare str) — leading `LABEL value` chunk on the status row, before the flag badges; see same section

### Per-probe quirks worth knowing

- **Hailo** — `get_chip_temperature()` returns both `ts0_temperature` and `ts1_temperature`; we expose them as separate `TS0`/`TS1` metrics. Power is firmware-side averaged via `start_power_measurement()`. Another HailoRT client (e.g. `hailortcli benchmark`) clobbers the averaging buffer; the probe auto-recovers after `_power_restart_threshold` consecutive `None` reads. HailoRT's C library logs an overcurrent-protection warning to stderr on every `start_power_measurement` — `_silence_fd_output()` redirects fds 1/2 around the call so it doesn't corrupt curses. `HailoProbe(bdf, sdk_device=<Device>)` also supports a **borrow mode**: when an embedding caller (e.g. an external project running an HailoInference VDevice) passes a pre-opened Device, the probe uses that handle instead of opening its own — eliminating the firmware-buffer contention by construction. Borrow mode is the symmetric counterpart to `AxeleraProbe(sdk_device=...)`; standalone mb-powermon never uses it. **Throttling state** is wired from `device.control._get_health_information()` (note the underscore — `pyhailort` 2025-10 renamed the public alias to a private method; `_probe_health_info()` accepts both). Four `state_flags` entries, ordered so the temperature pair groups together followed by the OCP pair:
  - **THERMAL** — `current_temperature_throttling_level`, a 5-state ladder rendered via the `_hailo_thermal_badge` formatter: `−1` → green ` OK ` (no throttling), `0` → yellow ` L1 ` (`temperature_orange_threshold`, default 104 °C → 350 MHz; per the Hailo user-config docs this is where "temperature throttling begins"), `1` → magenta ` L2 ` (108 °C → 300 MHz), `2` → red ` L3 ` (112 °C → 250 MHz), `3` → red+reverse ` MAX` (116 °C → 200 MHz). **MAX is the deepest graduated-throttling tier, not the absolute death cutoff** — `temperature_red_threshold` (default 120 °C) is a separate firmware setting where "all PCIe streams are forcefully closed" (chip stops responding entirely). Our 5-state ladder lives between "no throttling" and "PCIe shutdown"; the chip never actually reads above level 3 because it dies first. Curses has no "orange" in its 8-color palette, so the L2 tier is magenta — visually distinct from yellow (L1 below) and red (L3 above). MAX uses `A_REVERSE` so it stands apart from L3. All four tier thresholds are user-configurable via `temperature_parameters_source = USER_CONFIG_VALUES` in the firmware's flash/EEPROM config; we capture whatever the firmware reports at `_probe_health_info()` rather than hardcoding.
  - **TEMP_PROT** — `temperature_throttling_active`. **Despite the SDK name, this is the protection feature-enable bit, NOT a "has fired" latch** — confirmed by the Hailo user-config docs: `temperature_parameters_source = USER_CONFIG_VALUES` is the user-flash knob that activates the configured thermal thresholds, and the SDK field reflects whether that activation is currently in effect. Empirically verified by toggling `ctrl.set_throttling_state(False)` → both `temperature_throttling_active` and `overcurrent_throttling_active` flip to 0; `set_throttling_state(True)` → both flip back to 1. Healthy idle reads `1`. Rendered via the 4-tuple **plain form** (`_on_off_white_badge`, `plain=True`) — no brackets, no bold, plain-white `ON `/`OFF`. The flag de-emphasizes itself relative to the louder THERMAL / OCP indicators next to it; an `OFF` reading still pops in the row because it's the only place the text reads "OFF" rather than "ON".
  - **OCP** — `current_overcurrent_zone`. The SDK's `OvercurrentAlertState` enum exposes only `GREEN(0)` / `RED(1)` (binary). Per the Hailo user-config docs the firmware tracks one `overcurrent_monitoring_red_threshold` (mA), so the binary GREEN/RED zone is actually all that exists at the firmware level — there is **no** hidden 3-level + max structure analogous to temperature (the earlier speculative comment to that effect has been corrected). Renders via the default formatter (` OK ` / `ALERT`). OCP is available only on mPCIe and M.2 modules, not the PCIe AIC card — fine since mb-powermon targets the M.2 form factor.
  - **OCP_PROT** — `overcurrent_throttling_active`. Same enable-bit semantics as TEMP_PROT — backed by the docs' `overcurrent_throttling_enable` user-config field ("enables the overcurrent throttling option of the overcurrent monitoring component"). Same plain-form rendering with `_on_off_white_badge`. `OFF` means **someone has disabled overcurrent protection** — the genuinely-dangerous state, but at idle this nearly always reads ON, so the de-emphasized plain-white text is appropriate.

  **`state_prefix` = CLOCK** — current effective NN clock in MHz, rendered as the dim leading value on the status row (the convention shared with MemryX's CLOCK prefix). At THERMAL level −1 the value is `requested_temperature_clock_freq` (typically `400MHz` on Hailo-8). At levels 0/1/2/3 it switches to the per-level throttled clock captured from `temperature_throttling_levels` at probe time (350/300/250/200 MHz on the current firmware). The mapping is firmware-version dependent — captured once at `_probe_health_info()` rather than hard-coded.

  Status row at idle reads `CLOCK 400MHz  THERMAL [ OK ]  TEMP_PROT ON   OCP [ OK ]  OCP_PROT ON` (no brackets around `ON`/`OFF` — they're plain inline text). Under heavy load with TS0/TS1 at ~108 °C it'd shift to `CLOCK 300MHz  THERMAL [ L2 ]  TEMP_PROT ON   OCP [ OK ]  OCP_PROT ON` — the bracketed THERMAL badge and the CLOCK value pop while the plain-text protection flags stay put. CSV emits four integer columns plus the metrics: `<bdf>_THERMAL`, `<bdf>_TEMP_PROT`, `<bdf>_OCP`, `<bdf>_OCP_PROT`. The CLOCK prefix is display-only (not in CSV — derivable from `THERMAL` + the static per-level table). Wiring is gated on the capability probe succeeding at `_open()`, so older firmware that doesn't expose `_get_health_information` cleanly downgrades to empty `state_flags` (no status row at all).

  **No latch-clear API**. The firmware exposes no method to clear a "throttling event history" because no such latch exists — `current_overcurrent_zone` is the only event indicator, and it's self-clearing when load drops. A `c` keybinding to clear was considered but skipped: the only sysfs-adjacent controls are `set_throttling_state` (which **disables** the protection — opposite of "clear") and the heavy reset hammers (`chip_reset`, `soft_reset`, `nn_core_reset`) which disrupt active inference.
- **Axelera** — Metis M.2 doesn't expose power, so the `POW` history stays empty by design. Temperatures come from `triton_trace --slog --peek` (the binary is auto-located on `$PATH` or `/opt/axelera/runtime-*/bin`). The collector log line is `core_temps=[a,b,c,d,e]` — **5 values**, not 4 despite the name: index 0 is the Sys-core (module/system PVT monitor), indices 1–4 are AI-cores 0–3. We surface them as separate `SYS` / `AI0` / `AI1` / `AI2` / `AI3` metrics. There's also a `temp_sensor@40` board sensor referenced in Axelera's CONNECT docs (I²C addr 0x40 on the M.2's internal bus), but at firmware 1.5.3-1 it isn't exposed through any host interface — see the `mb-axelera` skill for the full investigation. The probe enables `--slog-level inf:collector` at startup and restores `err` on `close()`; if you forget to close the probe, verbose collector logs leak. **`state_prefix` = CLOCK**: captured once at `_open()` from `axr.Context().read_device_configuration(dev)["clock_profile"]` (the firmware's configured NN clock in MHz; boot-time setting on Metis M.2, not adaptive). The panel header reads `CLOCK <MHz>` with no state-flag badges — Metis firmware has thermal throttling configured (`hw_throttling = '105:10'`) but doesn't surface the live state machine to the host, so we render the CLOCK alone (see "Is there any throttling state available?" discussion for the full investigation).
- **DeepX** — DX_M1 (PCI vendor `0x1ff4`) doesn't expose power, so the `POW` history stays empty by design. Temperatures come from shelling out to `dxrt-cli -s` (auto-located on `$PATH` or `/usr/local/bin/dxrt-cli`); the `dx_engine` Python SDK is for inference only, not telemetry. The CLI's status block contains one line per NPU core — `NPU 0: voltage 750 mV, clock 1000 MHz, temperature 29'C` — and we parse temperature into `T0`/`T1`/`T2` (M1 has 3 NPU cores). Voltage and clock are documented as static constants on this device, so they're not graphed. Identity (firmware version, RT/PCIe driver versions, memory size) is parsed once from `dxrt-cli -i` at `_open()`. **`state_prefix` = CLOCK**: parsed from the same `dxrt-cli -s` line via a separate `_CLOCK_LINE_PAT` (kept separate from `_NPU_LINE_PAT` so a future SDK reordering doesn't break temperature parsing) on every poll. All three NPU cores report the same clock, so we cache the first reading; the panel header reads `CLOCK 1000MHz`. No state-flag badges — M1 firmware exposes no throttling-state API.
- **MemryX** — MX3 (driver `memx_pcie_ai_chip`, DKMS module `memx_cascade_plus_pcie`). Three independent telemetry sources, each gracefully degrading on its own:
   - **Per-MPU temperatures (hwmon, always available)** — driver registers `/sys/class/hwmon/hwmonN/` with `name="memx0"` and 16 `tempN_input` files; only the populated slots return values. On the 4-chip MX3-2280-M-4 SKU, `temp1..temp4` populate one per MPU (matching the MPU 0 → MPU 3 dataflow pipeline); on a 2-chip SKU only `temp1..temp2`. The probe autodetects how many MPUs are present and emits a corresponding `T0..T(N-1)` metric per chip. Scanning is hwmon-name-based (`scan_sysfs_memryx()` walks `/sys/class/hwmon` for `name="memx0"` and resolves the BDF via the `device` symlink) — no PCI vendor ID match needed, robust to MemryX's vendor ID not being in the public PCI registry.
   - **Per-chip thermal throttle state (vendor sysfs, always available)** — parsed from `/sys/memx<N>/temperature` via `MEMRYX_SYSFS_RE` (one line per chip in the form `CHIP(i) PVT3 Temperature: ... (ThermalThrottlingState: <0|1>)`; the PVT sensor index varies — firmware picks whichever on-die sensor reads hottest at read time — and the regex skips it with `.*?` between `CHIP(N)` and `ThermalThrottlingState`). This is the **only** per-chip throttle source — `mxa.get_thermal_state(device_id)` returns a single module-level enum (no `chip_id` arg; the firmware effectively ORs the per-MPU latches). Exposed as `state_flags = [("THERMAL_0", ...), ("THERMAL_1", ...), ..., ("THERMAL_{N-1}", ...)]`. The TUI groups these by prefix into one `THERMAL [ s0  s1  s2  s3 ]` widget; CSV emits one column per chip.
   - **SDK telemetry (`memryx.mxa`, optional)** — when the MX3 SDK is installed and `mxa.get_power(device_id)` returns a numeric reading: `POW` (mW → W, graphed on the standard `--power-max` axis), voltage (mV) and clock (MHz) into `last_snapshot` (operating-point info, not graphed), and module-level `POWER` state-flag from `mxa.get_poweralert()`. The probe also exposes `state_prefix = ("CLOCK", "<freq>MHz")` so the status row reads `CLOCK 850MHz  THERMAL [ OK  OK  OK  OK ]  POWER [ OK ]`. If the SDK is absent or capability-gated off, the `POW` deque stays `None`, `POWER` flag and `CLOCK` prefix are omitted, and the row collapses to just the per-chip THERMAL widget.
   - **`identity["arch"]` quirk**: avoid periods. The snapshot formatter does `str(arch).split(".")[-1]` to unwrap enum qualnames like `BoardType.METIS`, which would also strip `"M.2"` to `"2"`. MemryXProbe uses `f"M2 ({n}-chip)"`.
- **PMD2** — 10 rails are polled and stored in `last_snapshot` (used by `--once`), but only `PCIE1/2/3` + `TOTAL` are graphed to keep the panel readable. The PMD2's STM32 internal `Tchip` is the MCU's own temp, not the system's, and is deliberately suppressed.
- **INA228** — `BLINKA_FT232H=1` MUST be set before any Blinka-touching module is imported, because `digitalio` caches the platform decision on first import. The module sets it via `os.environ.setdefault` at the very top — do not import `board`, `digitalio`, or `adafruit_ina228` above that line. Up to four INA228s share one FT232H I2C bus at canonical addresses `{0x40, 0x41, 0x44, 0x45}`. After 3 valid voltage samples per sensor, the metric label gets a sticky rail tag (`P1` → `P1(3.3V)`); CSV header writes are deferred until this finalizes.
- **PCIe ASPM** — needs to read past byte 64 of `/sys/bus/pci/devices/<BDF>/config`, which is gated by `CAP_SYS_ADMIN` (unprivileged readers see a 64-byte truncation, not a permission error — the file is `0644` but the kernel refuses the read internally). `_read_pci_config()` falls back to `sudo -n cat` for passwordless-sudo accounts; otherwise the field shows `<needs root or sudo -n>`. The recommended workaround is a narrow sudoers entry that grants passwordless read on PCI config space only — `<user> ALL=(root) NOPASSWD: /usr/bin/cat /sys/bus/pci/devices/*/config` in `/etc/sudoers.d/mb-powermon-aspm` (mode `0440`). **Don't run the whole tool under `sudo`** to fix ASPM: `sudo python3` uses the system Python, which doesn't see the venv that holds the vendor SDKs (`hailo_platform`, `memryx`, `adafruit_ina228`, ...) — every SDK-dependent probe silently downgrades to ERROR. If a one-off root run is genuinely needed, invoke the venv's interpreter explicitly (`sudo /path/to/venv/bin/python3 mb-powermon.py`); for normal use, install the sudoers entry and run as your normal user.

### CLI / orchestration

`main()` resolves probes in two passes: scan-by-type (`scan_hailo_devices`, `scan_axelera_devices`, `scan_deepx_devices`, `scan_memryx_devices`, `scan_pmd2_devices`, `scan_adafruit_devices`), then instantiate via `probe_factories[type]()` in the order given by `--probe` (or `DEFAULT_PROBE_ORDER = ["adafruit", "hailo", "axelera", "deepx", "memryx", "elmorlabs"]`). The order is also the on-screen panel order — `adafruit` leads by default so external/ground-truth power readings sit above chip self-reports.

`--once` calls `do_snapshot()` (text) and optionally `write_csv_snapshot()`. The TUI path opens the CSV in line-buffered mode (so `tail -f` works) and emits one row per `--interval` via `TUI._csv_emit()`.

**`--once` field-name convention**: all field labels render **UPPERCASE** — `BOARD`, `PRODUCT`, `DESC`, `PART`, `SERIAL`, `PCIE`, `ASPM`, plus the per-metric labels (`POW`, `TS0`, `TS1`, `T0`..`T(N-1)`, `SYS`, `AI0`..`AI3`, `PCIE1`..`PCIE3`, `TOTAL`, `P1`..`P4`, ...), plus state-prefix / state-flag labels (`CLOCK`, `THERMAL`, `TEMP_PROT`, `OCP`, `OCP_PROT`, `POWER`, ...), plus probe-specific extras (`VOLT`, `THERMAL`, `PWR_ALERT` for MemryX; `RAIL <name>`, `AGGREGATE` for PMD2; `ERROR` for failures). Width is fixed at 10 chars via `:<10` so values align vertically. When adding a new field, follow the convention — don't slip in lowercase. **The MemryX SDK clock is rendered as `CLOCK` (not `FREQ`) for consistency with Hailo's `state_prefix` CLOCK** — the underlying snap-dict key (`frequency_mhz`) stays unchanged since it's internal API.

## Editing notes

- When adding a new probe type, register it in: the `_probe_list` validator, `DEFAULT_PROBE_ORDER`, `probe_factories`, the scan-results aggregation in `main()`, the help-overlay text, and `--device` filtering. Missing one of these is the typical bug.
- The git working tree is on a filesystem with mismatched UID ownership — `git` commands fail with "dubious ownership" until you run `git config --global --add safe.directory <path>`.
